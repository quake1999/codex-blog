过去一年，“智能体”逐渐从一个抽象概念变成了可以真正参与工作的工具。它不再只是回答问题，而是能够阅读项目、调用工具、修改文件、运行测试，并根据结果继续行动。

这篇文章不打算讨论遥远的通用人工智能，而是从一个更具体的问题开始：**今天的 AI 智能体究竟能做什么，以及怎样让它可靠地参与真实项目？**

我会结合这个博客的开发过程，记录一次完整的智能体实践。

## 什么是 AI 智能体

普通聊天模型的工作方式通常是“一问一答”。你提出问题，它根据已有上下文生成回复，任务到这里就结束了。

智能体则多了一层持续行动的能力。它会围绕目标形成一个循环：

- 理解当前任务和限制条件；
- 检查文件、代码或外部系统的状态；
- 选择合适的工具执行操作；
- 观察执行结果；
- 根据结果修正方案，直到任务完成或遇到需要人工决定的问题。

因此，智能体并不是单纯“更聪明的聊天机器人”。更准确地说，它是由模型、工具、上下文和反馈机制共同组成的执行系统。

> 模型负责判断下一步做什么，工具负责真正改变世界，验证则负责判断改变是否正确。

一个能够写代码但不能读取项目、不能运行测试的模型，只能提供建议；一个可以访问工作区、终端、浏览器和部署平台的智能体，才有机会完成端到端任务。

## 当前智能体能做什么

目前最成熟的应用仍集中在边界清晰、结果可以验证的工作上，例如：

- 阅读和整理代码库；
- 修改页面、接口和配置；
- 运行构建、测试与静态检查；
- 查询日志并定位错误；
- 编写或修改结构化文档；
- 操作 Git 分支、提交和部署流程；
- 在授权范围内连接外部服务。

这些任务有一个共同特点：智能体可以获得明确反馈。构建成功或失败、页面是否返回 200、某个文件是否存在，都是可以验证的信号。

相比之下，目标模糊、标准主观或后果不可逆的任务，仍然需要更多人工参与。例如品牌战略、重要商业决策、公开发布敏感内容，以及涉及账户权限和资金的操作。

## 我的实践：让智能体参与博客开发

这个博客最初托管在另一个网站平台，后来需要迁移到 Vercel，并希望使用 GitHub 在线编辑文章。整个过程包含了多种不同类型的工作：

- 分析原有项目结构；
- 将构建方式迁移为标准 Next.js；
- 把文章整理为 Markdown 文件；
- 创建 GitHub 仓库并同步代码；
- 连接 Vercel 与 GitHub；
- 验证自动部署是否生效；
- 为文章建立统一模板。

如果完全手工操作，需要在编辑器、终端、GitHub 和 Vercel 之间来回切换。智能体的价值并不是替我做出所有决定，而是把这些步骤串成一条连续、可验证的工作流。

### 第一步：先理解项目，而不是立即修改

智能体首先检查项目目录、依赖、构建脚本和文章数据来源。这个阶段很重要，因为同一个“博客”可能使用完全不同的技术方案。

只有确认项目使用 Next.js、文章位于 `content/posts`、部署目标是 Vercel 后，后续修改才有可靠依据。

这让我意识到，一个好的智能体工作流应当从“收集证据”开始，而不是从“生成代码”开始。

### 第二步：把修改变成可验证的闭环

每次功能修改后，智能体都会运行必要的检查：

- 使用代码检查发现语法和规范问题；
- 执行生产构建，确认所有文章页面都能生成；
- 在浏览器中检查页面和按钮交互；
- 部署后验证首页与文章页面的 HTTP 状态；
- 查看运行日志，确认没有新增错误。

这套过程比“一次生成很多代码，然后希望它能运行”可靠得多。

我现在更愿意把智能体看成一个会执行实验的协作者：每次只做范围明确的改变，然后立即观察结果。

### 第三步：用 GitHub 和 Vercel 建立自动发布链路

博客代码推送到 GitHub 后，Vercel 通过 GitHub App 监听仓库变化。当 `main` 分支出现新提交时，Vercel 会拉取对应版本，安装依赖并执行构建。

构建成功后，正式域名才会指向新版本；如果构建失败，旧版本仍然可以继续访问。

现在文章发布流程已经变成：

- 在 GitHub 新建或编辑 Markdown；
- 提交修改；
- Vercel 自动构建；
- 构建成功后自动上线。

智能体在这里承担的是配置、检查和排错工作，而 GitHub 保存每次修改的历史，Vercel 负责构建和托管。三者各自承担不同职责。

## 实践中遇到的几个问题

### 智能体必须尊重已有修改

当本地代码和 GitHub 同时发生变化时，直接推送可能覆盖在线编辑的文章。正确做法是先获取远端提交、比较差异，再用快进或变基方式合并。

这类问题说明，智能体不应假设自己是唯一的操作者。真实项目中，人和自动化工具可能同时修改同一份状态。

### “可以访问”不等于“可以修改”

博客访客可以看到公开页面，但只有拥有 GitHub 仓库写入权限的人才能直接修改文章。Vercel 也只能访问经过授权的仓库。

因此，工具连接必须遵循最小权限原则：只授权需要的仓库，只在必要时执行外部写入，对删除、公开发布和权限变更保持谨慎。

### 自动化仍然需要人工决策点

智能体可以完成大量重复操作，但有些决定应该保留给人：

- 是否公开发布某篇文章；
- 是否接受远端冲突中的某个版本；
- 是否连接新的账户或扩大权限；
- 是否执行不可恢复的删除操作。

可靠的智能体并不是永远不询问，而是知道什么时候可以继续，什么时候必须停下来确认。

## 我总结的使用原则

经过这次实践，我形成了几条简单原则：

- **给出清晰目标。** 与其说“优化一下”，不如说明要修改哪个页面、希望达到什么结果。
- **让智能体先检查现状。** 文件、分支、部署状态和已有修改都应该成为决策依据。
- **把大任务拆成小闭环。** 修改、测试、观察，再进入下一步。
- **保留版本历史。** 使用 Git 管理修改，避免无法恢复的覆盖。
- **区分本地与外部操作。** 修改本地文件和发布到互联网是不同级别的动作。
- **验证最终结果。** 代码写完不等于任务完成，用户真正访问到的页面才是结果。

## 智能体不会取代什么

智能体擅长处理步骤复杂但规则明确的工作，却不会自动理解一个人真正想表达什么。

它可以帮助整理文章结构、检查事实和修改措辞，但文章中的判断、经验和立场仍然来自作者。它可以让发布流程更短，却不能替代持续观察和认真思考。

对我来说，智能体最有价值的地方不是“代替我完成工作”，而是降低了想法变成作品之间的摩擦。以前需要查阅文档、切换平台和反复排错的过程，现在可以在同一条对话中逐步完成。

## 总结

今天的智能体还远非全能，但已经足以成为真实项目中的协作者。它能够理解代码库、调用工具、执行修改，并通过构建和页面结果验证自己的工作。

真正决定体验的，不只是模型能力，而是任务边界、工具权限、反馈机制和人与智能体之间的协作方式。

这个博客本身，就是我的一次智能体实践：文章记录思考，GitHub 保存变化，Vercel 自动发布，而智能体负责连接这些环节。接下来，我还会继续探索图片管理、内容校验和更完整的写作工作流。
